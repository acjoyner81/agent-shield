# 0003. Implement End to End Telemetry and Execution Flow

**Date**: 2026-09-14
**Status**: Proposed

## Summary

This feature wires together the entire request path from the Angular Portal to the Java MCP server and back to Splunk. It establishes the first working vertical slice (tracer bullet) of the platform, proving that requests can be routed, tools can be executed, and telemetry can be tracked across the whole system.

## Context

The platform currently has isolated components: a portal, a gateway, an MCP server, and a telemetry aggregator. While individual pieces are functional, there is no connected path. We need to implement the "plumbing" that allows a user action in the portal to trigger a tool execution in the MCP server and leave a verifiable trace in Splunk.

This feature depends on the `0001-telemetry-standard` for log formatting and the `0002-redis-to-splunk-aggregator` for shipping logs to the observability platform.

## Requirements

**User stories**:
- As a user, I want to trigger a tool execution from the portal so that I can see the result of an AI agent's action.
- As a developer, I want to see a complete set of logs in Splunk for a single request so that I can debug the entire flow from portal to MCP server.

**Acceptance criteria**:
- **AC-1**: The Python Gateway exposes a `/v1/tools/execute` endpoint that accepts a tool name and parameters.
- **AC-2**: The Gateway forwards execution requests to the MCP Server using a lightweight JSON-RPC over HTTP client.
- **AC-3**: The MCP Server executes a deterministic `echo` tool and returns the result to the Gateway.
- **AC-4**: Every hop (Portal, Gateway, MCP) generates a log entry following the `0001-telemetry-standard`.
- **AC-5**: A complete log sequence sharing a single `traceparent` is verified in Splunk via the HEC API.

## Options considered

### Option 1: Heavyweight Orchestration Layer
Implement a dedicated orchestration service to manage the state of every request.

**Pros**:
- Better control over long running tasks.

**Cons**:
- Adds unnecessary latency and another point of failure for a simple tracer bullet.

### Option 2: Direct Gateway Routing (Recommended)
The Gateway acts as a thin proxy that forwards requests to the MCP server and handles the telemetry wrap.

**Pros**:
- Minimal latency.
- Simple to implement and debug.
- Aligns with the "boring technology" principle.

**Cons**:
- Gateway becomes the bottleneck if complex orchestration is needed later.

## Decision

**Chosen option**: Option 2: Direct Gateway Routing

The Python Gateway will serve as the entry point, routing requests directly to the MCP server and managing the telemetry context for the request.

## Feature design

**API surface**:
| Endpoint | Method | Key inputs | Key outputs | Auth | Key errors |
|---|---|---|---|---|---|
| /v1/tools/execute | POST | tool_name:string (req), params:json (opt) | result:string, trace_id:string | bearer | 404 (tool not found), 502 (MCP down) |

**Value sourcing**:
| Action | Value produced / displayed | Source |
|---|---|---|
| Execute Tool | traceparent | Generated by Gateway (if missing) |
| Execute Tool | tenant_id | From `X-Tenant-ID` header |
| Execute Tool | tool_result | Returned from MCP Server |
| Log Event | log_payload | Derived from request context and `0001-telemetry-standard` |

**Key invariants**:
- The `traceparent` must be identical across all logs for a single request.
- No request should be forwarded to the MCP server without a valid `tenant_id`.

**Security model**:
Requests to `/v1/tools/execute` require a bearer token. The Gateway validates the token and extracts the tenant identity before forwarding to the MCP server.

**Configuration required**:
- `MCP_SERVER_URL`: The internal URL of the Java MCP server.

**Critical test scenarios**:
- Happy path: Portal $\rightarrow$ Gateway $\rightarrow$ MCP $\rightarrow$ Splunk; verify all 3 logs exist with same trace ID, verifies **AC-1**, **AC-2**, **AC-3**, **AC-4**, **AC-5**.
- MCP Failure: MCP server is down; Gateway returns 502 and logs the failure to Redis, verifies **AC-1**, **AC-4**.
- Missing Tenant: Request missing `X-Tenant-ID`; Gateway returns 400, verifies **AC-1**.

## Build plan

1. Implement the `/v1/tools/execute` endpoint in `gateway-python`, satisfies **AC-1**
2. Build the JSON-RPC HTTP client to call the MCP server, satisfies **AC-2**
3. Implement the `echo` tool in the MCP server, satisfies **AC-3**
4. Wire telemetry logging at each hop following `0001-telemetry-standard`, satisfies **AC-4**
5. Verify the full trace in Splunk via the HEC API, satisfies **AC-5**

## Consequences

**Positive**:
- Proves the core platform plumbing works end to end.
- Establishes the pattern for all future tool integrations.
- Validates the telemetry loop in a real-world scenario.

**Negative / tradeoffs**:
- The "echo" tool is a stub and doesn't provide real business value.

**Neutral**:
- Requires basic connectivity between the Python and Java containers.

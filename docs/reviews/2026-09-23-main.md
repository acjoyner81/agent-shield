## Summary

This change set ships API key lifecycle (Spec 0010), wires machine principals into the RBAC path, adds a usage-metering engine (Spec 0009) and quota gate for `/v1/chat/completions`, and wires the Angular portal dashboard/keys screens to live data. The key store and RBAC work is genuinely strong: SHA-256 digest-only storage, pipeline-atomic lifecycle writes, exact-match default-deny scopes, and a thorough AC-1..AC-8 test suite all check out. However, three headliner problems block a clean merge: the metering pipeline is dead end-to-end (worker shadowed method + stream-key mismatch + hardcoded billing period), the new tier-quota gate trusts unauthenticated request headers and runs before tenant binding (trivially bypassable), and the new frontend calls `/api/v1/...` paths that the gateway does not serve (404s swallowed silently).

## Major

### 🟠 Metering pipeline is dead end-to-end, `worker/stream_worker.py:111` / `gateway/telemetry.py:125`
**Problem**: Three compounding failures stop `agentshield.token.usage` events (Spec 0009 AC-1..AC-6) from ever being aggregated.
1. Emitters `xadd` to `telemetry:queue` (`gateway/telemetry.py:125`), but the consumer worker reads `agent_shield:telemetry_stream` by default (`worker/stream_worker.py:12`, `TELEMETRY_STREAM_KEY`), which nothing writes to. No compose env var overrides it.
2. `TelemetryWorker` defines `process_event` twice; the second definition at `worker/stream_worker.py:111` shadows the first (`:45`), so the idempotent `process_token_event` path never executes. The surviving method only acts on `event_type == "llm_execution"` or a top-level `"tokens_used"` key — CloudEvents emitted by `emit_token_usage` have `type: "agentshield.token.usage"` and tokens under `data` — a per-event no-op.
3. When it does fire it writes `billing:usage:{tenant}:{current_period}` with a hardcoded `current_period = "2026-09"` (`worker/stream_worker.py:134`), drifting forever.
**Why it matters**: Spec 0009 is marked done in `scope.md`/`AGENTS.md` but no token usage is ever persisted; `/v1/usage/summary` and the Stripe usage sync will always be empty in production — silent revenue/observability loss with no error raised anywhere.
**Suggested fix**: Delete the duplicate `process_event`, keep the RPC to `process_token_event`, derive the billing period from the event timestamp (not a constant), and reconcile the stream key so consumers read `telemetry:queue`. Add one worker-level test that pushes a real CloudEvent and asserts roll-up keys.

### 🟠 New tenant quota gate trusts spoofable headers and runs before auth, `gateway/dependencies.py:22`
**Problem**: App/route-level dependencies resolve before the endpoint's parameter dependencies (verified empirically). So `verify_tenant_quota` on `/v1/chat/completions` (`gateway/main.py:221`) executes before `resolve_active_tenant` binds `request.state.tenant_id`; it therefore always falls back to the client-supplied `X-Tenant-ID` / `X-Tenant-Tier` headers. Omitting `X-Tenant-ID` makes `tenant_id` falsy and the function returns immediately (`gateway/dependencies.py:25`), skipping the over-limit/tier check entirely; spoofing a different tenant or "enterprise" tier disables the cap for that request.
**Why it matters**: The tier token-cap gate (402) — the whole point of the file — is bypassable by any caller, in exactly the multi-tenant abuse/overage scenario it exists to prevent. The two existing tests (`test_billing.py::TestTokenQuotaThrottling`, `test_quota_concurrency.py`) only assert the header-driven behavior, so the bypass is uncaught.
**Suggested fix**: Make the quota check depend on the verified principal (e.g. take `tenant_id = Depends(resolve_active_tenant)` and read entitlement tier from the bound tenant state/Redis), never from request headers. Fix or remove the duplicated second code block (see Minor) at the same time.

### 🟠 Frontend calls backend paths that don't exist; new UI is dead on arrival, `portal-frontend/src/app/core/services/telemetry.service.ts:63`
**Problem**: `fetchUsageSummary()` GETs `/api/v1/usage/summary` and `KeysService` (`portal-frontend/src/app/core/services/keys.service.ts:16`) GETs/`POST`s/DELETEs `/api/v1/keys`. The gateway only serves `/v1/usage/summary` and `/v1/keys` (verified: the `/api/v1/...` variants return 404; the Angular dev proxy does not rewrite `/api`). The `error: () => undefined` handlers swallow the 404s.
**Why it matters**: The dashboard's "Total tokens processed / Requests processed / Model breakdown" cards and the new keys screen (create/list/revoke) silently never work — a functional regression dressed as a feature. The keys revoke/rotate contract is similarly unreachable from the UI.
**Suggested fix**: Either register `/api/v1` aliases for the keys and usage routers on the gateway (the codebase already double-mounts `/api/v1/telemetry/logs` and `/api/v1/billing/webhook`), or point the frontend services at `/v1/...` with a proxy rewrite. Do not swallow errors silently on these two calls.

### 🟠 `/v1/telemetry/logs` returns real cross-tenant data with no authentication, `gateway/main.py:164`
**Problem**: The GET handler previously returned hardcoded mock rows; it now returns `telemetry_history` — the last 100 entries written by any tenant via `POST /v1/telemetry/logs` — with no auth dependency on the route. Verified: `GET /v1/telemetry/logs` → 200 with no credentials. Additionally, the real history shape is `{tenant_id, level, message, timestamp}` (flat, snake_case from `TelemetryPayload`), which does not match the frontend `TelemetryLog` contract (camelCase `eventId/tenantId/costUsd/statusCode/evalPassed/traceId`), so once real logs exist the portal's pass-rate/failed/spend computations read undefined fields.
**Why it matters**: Anonymous cross-tenant telemetry exposure on a security product, plus a contract mismatch that will render the logs panel corrupt exactly when real data starts flowing.
**Suggested fix**: Gate the route behind `resolve_active_tenant` and tenant-scope the query; normalize the stored payload to the event shape the frontend expects (or migrate the frontend to the flat shape) so both branches agree.

## Minor

### 🟡 Duplicate dead code block and two Redis connections per request, `gateway/dependencies.py:36`
**Problem**: The function body contains a first circuit-breaker block (`:28-38`) followed by a redundant second full implementation (`:39-78`, inside a dangling triple-quoted string that resolves to a no-op), so every `/v1/chat/completions` request opens two async Redis connections and runs the over-limit check twice. The first connection is closed with the deprecated `.close()`.
**Why it matters**: Wasted connections per request and confusing dead code; the deprecation warning appears in every test run.
**Suggested fix**: Delete the first block, keep one connection (`aclose()`), single over-limit + tier check on the verified tenant.

### 🟡 Rotate is a TOCTOU race, `gateway/keys.py:171`
**Problem**: `rotate_api_key` reads meta, checks `status != "Rotated"`, then pipelines the write with no `WATCH`/atomic guard. Two concurrent rotates of the same Active key both pass the check and each mint a successor; the loser still writes its successor's index and meta, so two active keys exist and the old key's `superseded_by` is last-write-wins.
**Why it matters**: Silent duplicate credential minting violates the lifecycle invariant (a key has exactly one successor) and the 409 contract.
**Suggested fix**: Use a Redis `WATCH`/transaction (or Lua) around the read-check-write, or a version-guarded `hset`.

### 🟡 Grace-period events emitted synchronously on every in-window request, `gateway/auth.py:170`
**Problem**: `verify_api_key` performs the Redis writes and JSON emission (`emit_key_rotation`) synchronously inline for each passing grace-period request. A rotated key still in high-volume use spams the telemetry stream and serializes a network round-trip into the auth path.
**Why it matters**: Hot-path latency and unbounded event volume during a 24h grace window.
**Suggested fix**: Rate-limit the grace telemetry (e.g. once per key per hour) and don't let event emission block authentication.

### 🟡 Hardcoded token counts and suppressed telemetry failure, `gateway/main.py:277`
**Problem**: `emit_token_usage(input_tokens=100, output_tokens=50, ...)` hardcodes billing figures instead of using `mock_llm_response["tokens_used"]`, and the surrounding `try/except Exception as e: pass` swallows emit failures silently.
**Why it matters**: Metered billing will aggregate fabricated token numbers; failures are invisible.
**Suggested fix**: Derive token counts from the actual response metadata and at least log the exception.

### 🟡 New worker files are entirely untested, `worker/stream_worker.py:111`, `worker/stripe_sync_worker.py:15`
**Problem**: The metering-consumer branch and the Stripe usage-sync loop have no tests; the shadowing bug above is exactly the kind of thing a consumer test would have caught.
**Why it matters**: Per project test signal, new branching/error-handling logic should be covered.
**Suggested fix**: Add unit tests for the worker (`agentshield.token.usage` event → roll-up keys; malformed → DLQ) and for the sync delta (`reported_tokens` bookkeeping).

## Strengths

- The API-key lifecycle is well designed and well tested: digest-only storage proven by asserting the raw secret never appears in any Redis value, pipeline-atomic create/rotate/revoke, correct grace-expiry clock math, and exact-match default-deny RBAC shared by JWT and machine principals (AC-1..AC-8 all covered).
- `test_rbac.py` and `test_key_rotation.py` mock at the right boundaries (fake Redis, mocked MCP transport) so the real `verify_jwt → bind → require_permission` chain is exercised; `test_scope_absent_denied` correctly locks "no wildcards, no implicit roles".
- The telemetry emitter hardening (`emit_event` no longer raising when Redis is down, with a fallback client) is a genuine resilience improvement.
